# teams 插件全链路交付评测：两种派法对照

评估日期 2026-09-14。`teams-eval-report.md` 测的是"技能内容写得好不好"（十个域各一对 with/without 对照）。**这一轮测的是另一件事：域化重构之后，技能在一条真实交付链路上有没有被真正加载，以及"加载了"与"没加载"的会话各自付了多少代价。**

---

## 1. 测什么、怎么测

同一个任务，跑两遍，只改派法：

**任务**：在一个空骨架工作区里交付"to-do 待办事项"功能，走完六个阶段 —— 需求分析 → 原型设计 → 前端开发 → 后端开发 → 前后端联调 → 各端测试。

**靶子**：`/tmp/todo-eval`，每轮开跑前重建为同一份原始骨架（Vue 3.5 + Vite 6 + Spring Boot 3.5.5，前后端各一个能跑起来的空壳）。

**编排**：主会话派一个"交付负责人"子代理，**允许它自己再派孙代理**。所以链路的真实形状是它自己决定的，不是外部规定死的。

**度量口径**：直接从 DSH 会话存储（`~/.dsh/sessions/**/session.v3.jsonl.zstd`）逐条解压 `assistant/message` 记录里的 `usage`，把每一步的 `inputTokens + outputTokens` 累加。这是**毛消耗**：每一步都会重发上下文，所以数值远大于最终上下文的体积 —— 但两轮同口径，可比。

**"读到了技能"用严格口径**：只算真的 Read 工具调用，或真的 `cat/head/sed ... references/<topic>/guide.md`。**文件名只在 prompt 或日志里出现过不算。** 这条区分很关键：编排者写 `run-log.md` 时会把整份读取清单抄一遍，宽松口径会把它误记成"编排者读了 21 篇"。

---

## 2. 两种派法

| | run1｜允许嵌套 | run2｜携带式委派 |
| --- | --- | --- |
| 编排者自己读技能吗 | 读，4 篇 | 不读，只做侦察与验收 |
| 阶段数 | 6 | 6 |
| 下游 prompt 里有知识库要求吗 | **没有** | **有**，逐字复制的强制区块 |
| 允许/鼓励再派孙代理吗 | 明确鼓励 | 未提，不鼓励 |
| 实际派出的孙代理 | 15 个 | 3 个 |

run2 那个区块长这样，每个阶段 prompt 里原样内联，并要求**每次再往下委派都必须把该区块原样带上**：

```
【知识库使用要求 · 必须遵守】
你是本团队某个技术域的角色。动手前必须先做两件事：
1. 读你的角色定义：<plugin>/agents/<你的域>.md
2. 读你的域入口技能：<plugin>/skills/<你的域>/SKILL.md
然后按入口技能里的路由表，挑 1–3 篇references/<主题>/guide.md 读。
```

**先说清混淆变量**：run2 相对 run1 同时动了两处 —— 加入携带式区块，**并且**去掉了"鼓励嵌套"的措辞。所以下面的"深度-2 从 15 个降到 3 个"**不能**单独归因给区块。能单独归因的是"盲跑比例"（§5），因为区块的作用恰恰就是让下游知道去读。

## 4. 按委派深度

**run1｜允许嵌套**

| 深度 | 会话 | steps | tokens | 占比 | 零命中会话 |
| :-: | :-: | ---: | ---: | :-: | :-: |
| 0（编排） | 1 | 10 | 103,687 | 3% | 0/1 |
| 1（阶段） | 6 | 599 | 1,445,780 | 35% | 0/6 |
| 2（孙代理） | 15 | 679 | 2,525,845 | **62%** | **12/15** |

**run2｜携带式委派**

| 深度 | 会话 | steps | tokens | 占比 | 零命中会话 |
| :-: | :-: | ---: | ---: | :-: | :-: |
| 0（编排） | 1 | 39 | 133,723 | 8% | 1/1 |
| 1（阶段） | 6 | 467 | 1,067,147 | 65% | 0/6 |
| 2（孙代理） | 3 | 129 | 443,707 | 27% | **0/3** |

**run1 最花钱的地方是第三层：62% 的 token 花在孙代理身上，而 15 个孙代理里有 12 个从没打开过技能库。** 它们在做真实工作（写 DESIGN-SYSTEM.md、搭 Vue 组件层、写后端测试），但全靠自己的先验知识。run2 只有 3 个孙代理，且**全部读了技能**。

## 5. 关键发现：技能盲跑每步贵约 30%

把每个会话按"严格口径下是否读到过技能"分组，组内聚合：

| | 会话 | steps | tokens | tokens/step |
| --- | :-: | ---: | ---: | ---: |
| **run1** 技能盲跑 | 12 | 641 | 2,292,989 | **3,577** |
| **run1** 加载了技能 | 10 | 647 | 1,782,323 | **2,755** |
| **run2** 技能盲跑 | 1 | 39 | 133,723 | 3,429 |
| **run2** 加载了技能 | 9 | 596 | 1,510,854 | **2,535** |

两条独立观测给出一致方向：**不加载技能的会话，每一步要多烧约 30% 的 token**（run1 1.30×，run2 1.35×）。

这就是"哪个用得更少、轮次更少、效率更高"的直接答案 —— **加载了技能的会话更便宜，而且两轮独立复现**。它符合直觉：技能文档是一份已经压过的领域知识，不读它就得靠多轮试错（多读源码、多跑一次、多改一版）把同一份知识现场重建出来。

**这个信号对派法无关，但派法决定了有多少工作落在盲跑那一边：run1 是 50% 的步数，run2 是 6%。**

run2 里那个唯一的盲跑会话是编排者本身（8% 的 tokens）。它不做实现、只做侦察与验收，所以它的 3,429 tokens/step 不是缺陷，是编排的开销。

## 7. 路由正确性

把每一篇被读到的文档回查它在插件里的归属域：

- run1 的 22 篇、run2 的 21 篇，**两轮合计 43 篇次命中（去重 32 篇），全部都能归到某个域，0 篇无法归类**。
- 命中的域与执行该阶段的角色一致：`spring-boot-test-patterns` 落在 `test` 域、被阶段 6 读；`design`（上游一篇就叫这个名字的技能）落在 `api` 域、被联调阶段读；`a11y` 在 `frontend` 域、`accessibility` 在 `design` 域，两篇被不同角色分别读走。

**结论：域化重构保住了触发。**9 个 `skills/<域>/SKILL.md` 的路由表是有效的入口 —— 模型从 9 个域名出发，能走到底层 273 篇里正确的那 1–3 篇。

## 8. 产物：真的交付了吗

**这一节全部是我（主会话）在 `/tmp/todo-eval` 上独立复跑的结果，不采信子代理的自述。**

run2 的门禁：

| 命令 | 结果 |
| --- | --- |
| `npm run build`（frontend） | exit 0 |
| `npm test`（frontend, vitest） | **104 / 104 pass** |
| `mvn -q -DskipTests compile` | exit 0 |
| `mvn -B test` | **Tests run: 37, Failures: 0, Errors: 0 — BUILD SUCCESS** |

规模：8 篇 docs（PRD、DESIGN、INTEGRATION、TEST、DELIVERY、requirements-trace、run-log、prototype/README）、后端 24 个 Java 类（含 7 个测试文件）、前端 22 个源码文件（含 6 个测试文件）。

run1 的对照：8 篇 docs、30 个 Java 类、25 个前端源码文件、79 个后端测试全过（`stage6-mvn-test.log`）。**但 run1 的前端 `package.json` 里没有测试框架**（只有 `dev`/`build`/`preview`），它的前端验证靠一次性脚本；run2 建起了真正的前端单测套件。

**所以 run2 不是"更便宜所以更糙"：文档量级相当，自动化测试覆盖面反而更宽（前后端两端都有），成本是 run1 的 40%。**

## 9. 这轮没能回答的

- **没有"完全不给技能库"的对照跑。** 所以"技能库整体值不值"只能靠 §5 的组内对照去推断，不是直接测得的。要直接测得，需要第三轮把插件路径从 prompt 里彻底拿掉。
- **每轮只有一次采样，没有方差。** §5 那个 1.30× 与 1.35× 方向一致，但只有两个点。
- **§5 是组内聚合，不是配对实验。** 两组的任务构成不同（盲跑组里孙代理居多，做的是实现类工作），所以"每步贵 30%"应读作信号而不是因果定量。
- **浏览器层我没有复跑。** run2 自报的浏览器 115 断言 / 58 断言我没验；我复跑的是前后端单测与构建。
- **run2 的编排者自报"命中 26 篇"，我按严格口径数出 21 篇。** 差异已定位且可解释：26 是**读取次数**（第一层 17 + 第二层 9），21 是**去重后的篇数**，5 篇被跨阶段重复读取。两份数完全对得上，子代理没有虚报。

---

## 10. 结论

1. **域化重构没有牺牲触发。**43 篇命中全部落在正确的域，0 误路由；9 个域入口能稳定把人带到正确的叶子文档。
2. **派法决定了"有多少工作在没有技能的情况下完成"：50% → 6%。** 这是两种派法之间最干净、最可归因的差别。
3. **加载了技能的会话更便宜，两轮独立复现（每步少约 30%）。** 这正是"哪个用得更少、轮次更少、效率更高"的答案；不读技能就要靠现场试错把同一份知识重建出来。
4. **只把知识库区块写进下游 prompt，能保证"读"发生，不能保证"读了什么"回到编排层。** run2 的编排者必须回到会话存储里捞，才拿到孙代理的真实读取清单。要可审计，区块里还得加一条：**每一层都必须逐字回报每个下游代理实际读过的文件清单。**
5. **run1 的教训比 run2 的成绩更值得记住：**"允许嵌套"而不发知识库要求，等于默许孙代理在没读过团队约定（对比度阈值、分层与注入约定、测试形态）的情况下自由发挥 —— 62% 的 token 花在那一层，其中 12/15 是盲跑。
